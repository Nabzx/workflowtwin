# ADR 0002: Versioned append-only referral events

- **Status:** Accepted
- **Date:** 2026-07-16

## Context

WorkflowTwin must reconstruct a messy administrative referral process, distinguish source activity
from data arrival, reproduce analyses, and detect duplicates. The model must not imply clinical
decision-making or collect unnecessary patient information. Updating an event in place would erase
what an earlier analysis observed and weaken auditability.

## Decision

Represent one referral process instance in `referral_cases` and its recorded facts in
`referral_events`. Use UUID primary keys generated by the application and a separate documented
external identifier for each source record. Domain contracts and database rows carry schema version
`1`.

Store `event_at` and `ingested_at` separately as timezone-aware timestamps. Operational ordering
uses event time; analysis reproducibility uses an ingestion watermark. Do not enforce an ideal event
sequence in the domain or database.

Treat events as append-only. Frozen Pydantic contracts prevent ordinary mutation, SQLAlchemy hooks
reject ORM update/delete operations, a PostgreSQL trigger rejects direct event update/delete, and
the case foreign key restricts deletion. The unique pair `(source_system, external_event_id)` makes
duplicate ingestion fail predictably.

Use explicit string-valued vocabularies and database check constraints for stable operational
concepts. Use JSONB only for optional, structured, non-sensitive event attributes that do not yet
justify columns. Identity, ordering, filtering, lifecycle, actor, channel, reason, and manual-work
fields remain first-class columns. Metadata keys associated with clinical or direct patient data are
rejected by the domain contract.

## Rationale

- A case table supports current-state and date-range queries without deriving every fact repeatedly.
- Append-only events preserve the evidence used by previous analyses.
- Separate timestamps support late and out-of-order ingestion without rewriting history.
- UUIDs avoid coordination and remain stable across fixture generation and imports.
- Source-scoped external identity reflects how upstream systems usually guarantee uniqueness.
- String vocabularies are inspectable in SQL and easier to evolve through reviewed migrations than
  PostgreSQL-native enums.
- Bounded JSONB avoids a wide sparse table while preventing important analytical fields from hiding
  in opaque metadata.

## Consequences

Corrections must be represented by a new event rather than editing the original fact. Case status is
a current projection and may be updated, while event history remains unchanged. Database-owner
maintenance can bypass practical controls and therefore requires an operational audit procedure.

Adding vocabulary values or schema versions requires a migration and compatibility review. Late
events can revise metrics, so every analysis run must eventually store its ingestion watermark.
Version 1 does not provide a full source-payload archive, bitemporal corrections, event signing, or
cryptographic tamper evidence.
